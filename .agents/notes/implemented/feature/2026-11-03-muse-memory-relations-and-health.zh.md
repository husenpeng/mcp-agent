# Agent Note: Muse 记忆的关系、来历与存储健康

Status: implemented

[English](2026-11-03-muse-memory-relations-and-health.md) | 中文

## 问题

`tomato_memory` 每条记录存一行。模型可以按词搜索这些行，但记录始终是孤立的：没有任何东西把它与旁边写下的决定连起来；它已经保存的 `source` 既到不了模型也到不了人；也没有任何入口报告存储用了多少。Hindsight 通过把记忆组织成层次来补上这些缺口——实体关系、引用证据、合并精炼、项目知识页——并且把这些层次放在一个服务之后。可被本地插件复现的是这些层次，而不是 HTTP 服务本身。

## 决定

在 `@tomato/experimental-memory` 及其消费方上增加只读层，不改存储、不改配置，也不发起辅助模型请求。

`related(view, id, depth)` 从一条生效记录出发，走到同一 `entity` 的记录、同一会话写入的记录，以及共享 `key` 的记录。遍历只在视图内进行，每条记录只访问一次，最多走 `MAX_RELATION_DEPTH`（2）跳，并按发现顺序最多返回 `maxRecallResults` 条。候选记录或视图之外的记录不会到达任何内容。

`memory_related` 是第 4 个工具。它返回每条到达的记录，以及所经的关系、跳数和写入它的会话；写入注明了引用消息时还包含该消息。被委派的智能体也可以读取它，因为它不改变任何记忆。`stats(view)` 与 `/memory stats` 报告已存、生效、候选与置顶的条数、两个范围的上限，以及最早的生效更新时间。`/memory show <id>` 打印一条记录及其会话和引用消息，让人能核验这条记忆为何存在。

每条边都由记录已有的字段派生，因此没有引入边表、索引或迁移。

## 考虑过的替代方案

**用向量或向量索引找相关记录。** 该包没有 embedding 提供方；引入一个会把零依赖的实验插件变成需要索引生命周期、模型路由和重建索引策略的插件。结构化边已经能回答“围绕这条记录决定过什么”，不需要这笔代价。

**把边持久化到第二张表。** 边是 `entity`、`key` 与 `source.sessionId` 的纯函数；存下来只会复制记录，并在每次写入和删除时增加维护。

**让模型推断关联。** 同一段文本可以用语义连接，但请求成本会落到每次写入上，而且结果不可验证。它以后仍可作为产出候选记录的一轮处理出现。

**增加 `memory_status` 工具。** 这些计数服务的是决定清理什么的个人，而不是执行任务的模型；第 5 个 schema 会让每次请求都为与任务无关的内容花掉前缀 token。

**把候选记录纳入遍历。** 候选按设计对后续会话不可见；把它们走进去，等于从侧门把未确认内容泄漏到模型界面。

## 后果

- 每次请求携带 4 个记忆工具 schema，而不是 3 个。搜索、写入和快照路径没有变化，所以 KV 缓存影响仍只限于工具列表。
- 关系是结构化的：两条意思相同但没有共享 entity、key 或会话的记录不会相连，两跳也会错过更长的链条。该限制由[包 README](../../../../packages/experimental/memory/README.zh.md) 负责记录。
- `stats()` 与其他读取一样会扫描整个视图；各范围的上限限制的是开销，而不是域的大小。
- 两个包的覆盖率保持 100%。没有随包发布的快照 profile 挂载 Muse 组合包，因此没有录制会话语料需要更新；组合包的真实组合测试用脚本化模型启动这一行。
- 此次变更止于只读入口。词法重复提示随后由[重复提示笔记](2026-11-03-muse-memory-duplicate-hints.zh.md)记录，确定性的工作区索引由[项目索引笔记](2026-11-03-muse-project-index.zh.md)记录，回合后的候选捕捉由[捕捉笔记](2026-11-03-muse-turn-capture.zh.md)记录；由模型撰写的知识页仍未实现。
