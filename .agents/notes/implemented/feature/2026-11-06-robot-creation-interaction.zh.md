# Agent Note：把机器人创建改成引导式流程

Status: implemented

[English](2026-11-06-robot-creation-interaction.md) | 中文

## 问题

机器人创建有两条互相矛盾的路径。手动表单打开规格编辑器，却只要求填名称：一份未完成的草稿会以 `New robot` / `Describe what this robot does.` 发布，立刻变成一个执行空壳任务的机器人。对话路径把一段很长的元指令当成用户自己的第一条消息发出去，`robot-creation` 技能又在一句话里抛出四个问题，用户只能把表单当散文来回答。创建完成后用户留在工作区会话里，没有回到机器人的入口，重名冲突也要等到整套问答结束才暴露。

## 决定

创建改为机器人页内的三步流程：每次运行要做什么、名称与一句话描述、可选的成功标准与预览。流程要求真实的任务目标与名称，发布前在注册表里检查重名，预填页面正在查看的工作区目录，并就地发布规格、实例化机器人。它绝不接受 `emptyRobotSpec()` 里的占位名称或占位任务；缺少回答时退回需要回答的那一步，provider 拒绝时留在流程内显示原因。规格编辑器改为纯编辑界面：同样校验两个必填字段，并保留高级标签页。

对话路径继续使用会话，但换掉启动请求：页面发送一句用户口吻的短请求，而不是元指令。`robot-creation` 技能一次只问一个问题，部署挂载 `ask_user_question` 时用表单卡呈现，描述由技能自己起草，展示四项草稿并等待确认，确认后才调用 `robot_create`。

`robot_create` 会以 `ROBOT_SPEC_INVALID` 拒绝空白或占位的名称与任务目标，并指明需要补问的字段。成功结果把 `{ robotId, name }` 记录为展示元数据，`@tomato/client-ui-robot` 据此渲染专属的 `robot_create` 工具行，并提供「打开机器人」按钮；按钮会选中该机器人并打开面板。这一行就是创建会话回到机器人的入口。

## 考虑过的替代方案

**保留编辑器作为唯一创建入口，只加校验。** 只加校验能修掉占位机器人，却仍让四十个控件成为第一印象；引导流程每一步只问当下真正要做的决定，并说明高级项沿用默认值。

**用一个 `ask_user_question` 批次问完四个问题。** 单张表单更短，但一次给出四个空字段，也没有地方解释任务目标为什么重要；一次一问让模型在用户继续投入注意力之前，先对含糊回答做一次追问。

**继续把长启动提示当作可见的用户消息。** 那条提示看起来像用户自己输入的内容，泄露了 harness 术语（`skill`、`robot_create`），还让助手把同样的指令复述一遍。短请求依靠技能描述触发，不需要这些词。

**让工具接受任意任务目标字符串。** 模型可以用占位文本满足必填字段，这正是现有空壳机器人的来源；工具现在拒绝该值，并告诉模型该补问哪个字段。

## 后果

- 客户端流程与 `robot_create` 都无法再用占位名称或占位任务发布机器人；旧记录保持原值，直到有人编辑。
- 创建会话仍会离开机器人页，因为它是真实的工作区会话；创建成功那行的「打开机器人」是记录在案的返回路径。
- 工具结果 schema 未变，既有 Session 可以重放；展示元数据是新增的，只有机器人工具行读取它。
- 客户端流程、技能、工具校验与工具行分别由 `create-flow.client.spec.tsx`、`robot-create-row.client.spec.tsx`、`page.client.spec.tsx`、`config-editor.client.spec.tsx`、`robot-tool.spec.ts` 与 `robot-app.spec.ts` 覆盖。
- 两个包 README 与机器人子系统页在两种语言下都描述该流程、一次一问的访谈与工具行。
