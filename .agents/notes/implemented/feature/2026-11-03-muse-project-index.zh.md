# Agent Note: Muse 回合开始时的项目记忆索引

Status: implemented

[English](2026-11-03-muse-project-index.md) | 中文

## 问题

回合快照展示画像记忆和置顶的工作区值，但模型看不到这个项目还在哪些主体上存过记忆。它要么盲目搜索、每个会话都用同样几个显眼词，要么干脆不搜。Hindsight 用知识页回答这个问题：一份由模型维护、智能体开工前先读的 wiki。那份页面每次变化都要一次模型请求，还要一份缓存来保持最新，而这个实验层不打算付这笔代价。

## 决定

当 `projectIndex` 开启时，回合快照消息会在已记录的快照之后继续输出工作区的主体索引：

```text
Project memories by subject (counts only; memory_search returns the values):
- client:acme: 4 (budget, contact, deadline, email-tone)
```

一个主体至少拥有 `MIN_INDEXED_RECORDS`（2）条生效工作区记忆后才会出现。行按条数、再按主体名排序；最多 `MAX_INDEXED_SUBJECTS`（8）个主体、每个最多 `MAX_INDEXED_ATTRIBUTES`（6）个属性，多出的以 `…` 表示，主体被裁剪时追加 `(<count> more subjects omitted; memory_search by subject.)`。索引只带主体、条数和属性名，从不带值。

索引与既有快照共用同一条消息及它的摘要，因此记录集不变时后续回合仍不增加内容。字节预算上值优先：先渲染快照，索引最多使用剩余空间且上限 1024 字节；宁可让索引消失，也不把一条置顶记忆挤出去。`projectIndex` 是带校验的配置字段，默认开启。

## 考虑过的替代方案

**为每个主体列出值。** 那会重复 `memory_search` 返回的内容，随存储增长，并把快照预算花在模型可能并不需要的内容上；条数与属性名足以引导搜索，而不必倾倒内容。

**用模型生成知识页。** Hindsight 的知识页更好读，但每次记录变化一次请求、一份修订缓存以及无法验证的重写，对实验性的回合快照并不成比例。确定性的索引以后可以长成模型撰写的页面，而无需改变消息来源或摘要逻辑。

**把索引注入为第二条消息。** 它需要自己的来源类型、快照登记和重复抑制；现有消息已经具备这三者。

**无视快照、总是渲染索引。** 它会与置顶值争夺同一份预算；人置顶的值比一条指向未置顶内容的指针更重要。

**连只有一条记忆的主体也索引。** 多数主体从一条记录开始，这样索引会列出几乎所有内容，失去定位价值。

## 后果

- 索引只列名称和条数，不列陈述：只有一条记忆的主体不可见，关于不同主体的两条记忆也不会因为索引而被关联。
- 快照占满 `maxSnapshotBytes` 时不会出现索引；这个配置上限同时约束两部分。
- 文本是模型可见的，因此包 README 的快照约定、两种语言的 README、两种语言的配置目录以及快照测试都会变化。不涉及工具 schema、存储或工具数量。
- 覆盖率保持 100%。本层扩展的层次记录在[关系与健康笔记](2026-11-03-muse-memory-relations-and-health.zh.md)，写入期的合并精炼记录在[重复提示笔记](2026-11-03-muse-memory-duplicate-hints.zh.md)。
