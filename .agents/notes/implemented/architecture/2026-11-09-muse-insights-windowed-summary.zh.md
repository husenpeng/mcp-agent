# Agent Note: Muse 回顾只总结新增证据

Status: implemented

[English](2026-11-09-muse-insights-windowed-summary.md) | 中文

## 问题

最初的 Muse 回顾总结整个本地日期，并在每次尝试时替换此前的回顾。随着当天内容增长，每次运行都会重新读取并重新发送所有会话与消息，而字节上限会裁掉本已过长的输入的尾部；模型看到的是当天不断缩小、任意截取的一部分，描述的工作越多，回顾反而越不准确。两个节奏键也名不副实：`recapIntervalMinutes` 控制同一天回顾的重试间隔，而可见弹窗每天只出现一次；`taskIntervalMinutes` 只控制未完成任务分析。于是设置 4 小时的回顾并不会产生用户看得见的周期性回顾。

## 决策

Host 只总结比已保留回顾更新的证据。`collectDay` 接受一个排他的 `since` 时刻，取已保留回顾的 `latestEventTime`，因此每次运行只读取当天顶层会话中该时刻之后的人类与助手文本；当天第一次运行仍读取整日。

限长后的请求是 `{ previousRecap, newSessions }`。`previousRecap` 携带当天当前标题、摘要、工作项（含 `sessionIds`）和开放任务；`newSessions` 携带每个新会话的 id、标题和消息。模型返回完整更新后的回顾：既有工作项在多次运行之间保持措辞，并在新证据确定结果时更新状态或方案，新工作项引用两部分中的会话 id。`parseRecap` 用新会话与既有工作项的 id 校验会话 id；Host 把窗口内的消息数加到保留总数、按身份合并会话摘要，并保留最新的模型交换。输入裁剪先删除最旧的新消息，再删除此前回顾的工作项细节，因此上限约束请求的同时不会丢掉当天叙述。

模型调用失败仍不会替换已有回顾，没有新文本的运行不写入任何内容。确定性窗口回顾不会覆盖模型写成的当天回顾。

配置拆分了两种节奏。`recapNoticeMinutes`（240）是浏览器弹窗间隔，随每次快照下发，由控制器同时用于回顾与未完成任务提示。`summaryIntervalMinutes`（120）是一次总结运行的间隔，该运行刷新回顾和任务分析；快照也会在当天回顾早于该间隔时请求一次运行，因此没有 timer 的 Client 仍会刷新。节奏变化时重启计时器的行为不变。

`provider` 与 `model` 默认是 `blueai` 与 `DeepSeek-V4.1-Flash-1017`，即随产品部署配置的路由，两者仍需同时提供。配置页把它们渲染为选择框，选项来自 `llm-pi-ai` 设置段声明的提供商与模型（通过共享的 `configForms` 读取）；该段之外的已存路由仍保持可选。

## 考虑过的替代方案

**保留整日输入并收紧字节上限。** 这保留了现有请求，但每次运行仍重读整日，仍会在没有可信任优先级的情况下截断；本次要解决的不准确恰恰来自截断。

**只发送新窗口，由 Host 合并工作项。** 模型必须看到既有工作项才能更新其状态，而由 Host 合并模型措辞要么冻结状态，要么凭空发明工作项身份。携带 `previousRecap` 让写出这些内容的模型保留身份与措辞。

**每天限制弹窗次数。** 用户要的是可配置的弹窗节奏；按天计数会让 4 小时设置在一天的大部分时间失效。间隔是唯一规则。

## 后果

模型可见输入变为 `previousRecap` 与 `newSessions`；已存回顾的 `model.input` 是该版本的完整材料。存储记录保持格式版本 1，因此无需数据迁移，旧回顾会在下一次运行时作为此前回顾提供。部署未配置的路由仍会退化为确定性回顾并记录失败。长日子每次运行累积一个版本，更早的版本及其精确交换不会保留。即使某次运行没有新增证据，弹窗仍会重复最新回顾。
